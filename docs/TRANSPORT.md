# Прозрачная передача через Figma

**Текущий сценарий по D-13:** на каждом ПК выбирается один собственный каталог проекта. Между ПК данные идут только через Figma; предпочтительный путь без плагина — ручная вставка зашифрованного текста на холст и копирование содержимого текстового слоя на другом ПК. Приём и сравнение используют полученный пакет, а не путь к удалённой папке. Реализован пока только [локальный диагностический comparator](LOCAL-COMPONENT.md); передача, упаковка и шифрование отсутствуют.

2026-10-20 пользователь подтвердил: **«Передавать код через Figma разрешено»** (D-10), затем уточнил canvas copy/paste и преимущественно поочерёдную работу с ручным merge (D-13). Это требование к потоку, а не доказательство технической доставки.

## Предпочтительный путь без плагина

1. На ПК A выбрать свой локальный проект и нажать «Экспорт»: проверить состав, получателя и создать зашифрованный текст для копирования.
2. В Figma вставить текст в явно обозначенный текстовый слой на холсте. Если пакет требует частей, каждая часть относится к одному package ID и нумеруется; допустимые размеры ещё предстоит измерить.
3. На ПК B скопировать именно содержимое текстового слоя. В figmobil нажать «Импорт», вставить полученный текст/части и выбрать свой локальный профиль проекта.
4. Локально проверить комплектность, целостность, происхождение и получателя, расшифровать и показать сравнение. Затем пользователь явно выбирает применение; отсутствующая/неизвестная база и конфликт не приводят к слепой записи.
5. Merge с коллегами пользователь делает самостоятельно своими инструментами. После этого новый ручной экспорт результата на B → Figma → импорт на A замыкает цикл. Оба направления поддерживаются одинаково; работа одновременно с двух сторон не предполагается как основной сценарий, но локальные расхождения всё равно защищены.

Одна привязка проекта означает один локальный каталог на каждом ПК. Incoming и база — внутренние данные приложения; пользователь не должен вручную поддерживать третью папку или указывать адрес другого ПК. Figma переносит зашифрованные данные, вычисление сравнения и расшифровка выполняются локально. В Figma не публикуется расшифрованный diff.

Приложение должно связывать пакет с project ID, package ID и точной базовой версией, отвергать неполный/смешанный/устаревший пакет и безопасно обрабатывать повтор. Общая база меняется по подтверждению точной принятой версии обеими сторонами. Экспорт, доставка и расшифровка по отдельности не являются таким подтверждением. После частичного применения или ручного merge нельзя объявить всё дерево общей базой: до отдельного решения MVP удерживает прежнюю базу. Подтверждения проходят тем же ручным каналом Figma.

Официальное [руководство Figma по тексту](https://help.figma.com/hc/en-us/articles/360039956434-Guide-to-text-in-Figma-Design) подтверждает создание текстовых слоёв инструментом T и вставку содержимого в режиме редактирования. Это основание для прототипа, но не подтверждение побайтовой сохранности больших пакетов. Нужен ручной A → B → A на синтетическом шифротексте: exact-byte roundtrip, размеры/части, пропуск/повтор/подмена фрагмента, копирование содержимого слоя и задержка синхронизации. Ничего в Figma пока не создано и не отправлено.

## Лимит выдачи текста: 5 МБ в минуту (D-15)

Считаем десятичные МБ: максимум **5 000 000 байт за любые 60 секунд**, а не только по границам календарной минуты. Размер относится к готовому сериализованному тексту UTF-8 после шифрования, текстового кодирования и добавления всех заголовков/служебных полей. Повторные выдачи и подтверждения также расходуют лимит; исходный или сжатый размер проекта не заменяет этот счётчик.

Независимый компонент политики `internal/transferlimit` ограничивает одну часть 250 000 байтами и выдаёт разрешение не чаще раза в 3 секунды. Маленькая часть также занимает интервал. Простой не накапливает разрешения; в полуоткрытом скользящем окне `(t−60с, t]` возможно не более 20 выдач, то есть не более 5 000 000 байт. При отказе возвращается время ожидания; компонент не спит, не копирует текст и не запускает фоновых операций. Следующая выдача по-прежнему требует явного нажатия.

**Это политика для будущего транспорта; текущий comparator её не вызывает.** При интеграции нужен один общий gate на устройство для всех проектов, операций и направлений, серверная проверка до выдачи полного текста любым UI/API-путём, блокировка второго владельца процесса, отсутствие возврата квоты после выданного разрешения и countdown. После приобретения единоличного владения новый gate выдерживает начальные 3 секунды; создавать его заранее перед ожиданием lock нельзя. Часы backend используют монотонное время; rollback обрабатывается отказом. Повторное открытие окна не должно создавать независимую квоту. A-15 принимает чистую политику, A-16 — её последующую общую интеграцию.

Разрешение проверяется непосредственно перед выдачей уже готовой части. Нельзя заранее накапливать разрешения для отложенной пакетной выдачи; задержанный handoff и последовательность завершений должны проверяться при интеграции отдельно от времени admission.

Приложение может ограничивать выдачу частей и обработку импорта своими командами. Оно не управляет внутренним сетевым трафиком/повторами синхронизации Figma и не может запретить человеку повторно вставлять уже скопированный текст. Поэтому лимит реальной сетевой полосы Figma здесь не обещается. Выбранные 250 000 байт — верхняя граница политики, а не измеренная вместимость текстового слоя; прототип может потребовать меньшие части.

## Архив прежнего предложения с плагином

Следующие разделы оставлены как исторический кандидат. Они не задают текущий основной UX без плагина.

## Предлагаемые компоненты

1. Локальное приложение `figmobil.exe`: выбор проекта, сохранение байтов файлов, шифрование и проверка пакета, предпросмотр конфликтов и подтверждённое применение. Одинаковая версия на обоих ноутбуках, без фоновых служб и автоматических сетевых операций.
2. Собственный видимый плагин `figmobil` в Figma Desktop: пользователь выбирает зашифрованный пакет и явно отправляет его в выделенную область документа; на втором ноутбуке явно получает пакет. Плагин работает только в открытой пользовательской сессии и не получает приватные ключи.

Для прежнего варианта требовалось отдельно проверить подключение плагина на первом ноутбуке. Плагин не создан и не установлен; существующий локальный comparator сделан отдельно и не реализует этот путь. Исходники, manifest и инструкции любых будущих компонентов доступны для просмотра до установки.

Кандидат оболочки — [Wails v2.17.0](https://github.com/wailsapp/wails/releases/tag/v2.17.0), Go и компонентный интерфейс TypeScript/React. Wails имеет [MIT license](https://github.com/wailsapp/wails/blob/master/LICENSE) и на Windows [требует WebView2](https://v2.wails.io/docs/gettingstarted/installation/). Наличие подходящего WebView2 на первом ноутбуке не проверено; приложение не должно незаметно устанавливать runtime. Go/Node/npm нужны для разработки, а не как отдельная предполагаемая установка на первом ноутбуке.

Для локального шифрования рассматривается Go library [age v1.3.2](https://github.com/FiloSottile/age/releases/tag/v1.3.2), [BSD-3-Clause](https://github.com/FiloSottile/age/blob/v1.3.2/LICENSE). Отдельный age.exe тогда не нужен. Это кандидат до проверки зависимости и интеграции; шифрование получателю само по себе не подтверждает отправителя. Аутентичность и первичная сверка доверенных ключей остаются частью A-02.

## Пользовательский путь

На каждом ноутбуке одинаковые ручные операции:

- Экспорт: в локальном приложении выбрать проект и файлы, проверить состав, создать зашифрованный пакет. В плагине выбрать этот пакет, увидеть его размер и явно подтвердить отправку в Figma.
- Импорт: в плагине выбрать видимый пакет и явно получить его. В локальном приложении выбрать полученный пакет и рабочую копию, проверить содержимое, увидеть изменения/конфликты и подтвердить применение.

Переход между приложением и плагином пока предполагает явный файловый ввод/вывод. Это не обещание одного клика на весь путь и не скрытый локальный HTTP-сервис. Удобство пути проверяется на прототипе до фиксации UI.

В документе размещается явно обозначенная область `figmobil — зашифрованная передача` с состоянием пакета. Никаких маскирующих элементов или скрытых слоёв. Набор метаданных минимален: содержимое проекта, имена файлов и приватные ключи не публикуются. Очистка полученного пакета — отдельное явное действие, без обещаний удаления серверных копий. Получение пакета и успешное применение — разные результаты.

## Подтверждённые возможности и непроверенное

Официальная документация [разделяет код сцены и UI iframe](https://developers.figma.com/docs/plugins/how-plugins-run/). UI может использовать браузерные API, код плагина — работать с документом; данные передаются сообщениями. [Документация UI](https://developers.figma.com/docs/plugins/creating-ui/) описывает работу с файлами и сообщениями. Это не даёт произвольного доступа к каталогу проекта и не подтверждает возможность сохранения по любому локальному пути.

Выбор файла через UI и сохранение полученного пакета необходимо проверить именно в Figma Desktop. Универсальная загрузка через Blob/download не считается гарантированным API Figma до испытания. Не заявляются неограниченные объёмы, мгновенная синхронизация или работа закрытого плагина.

После разрешения конкретных компонентов нужен короткий прототип на случайных тестовых байтах: ручная передача A → B и B → A, побайтовая проверка полученного файла, неполное/повреждённое содержимое, повторное получение и задержка синхронизации. Сначала выбираются измеренные ограничения размера; произвольный предел TextNode не объявляется документированным фактом. Закрытие/открытие плагина ничего не отправляет и не импортирует автоматически.

Проверки транспортного прототипа не заменяют A-02/A-08/A-09: реальное шифрование, сохранность Git diff и сборка переносимого проекта принимаются отдельно.
