# Двусторонний импорт и чистый Git diff

Статус: обязательный контракт и локальная реализация по D-16. Побайтовые снимки, планирование, подтверждаемое применение и восстановление проверены на синтетических данных Windows. Это не приёмка двух целевых ноутбуков: P1, полный браузерный сценарий и реальный A ↔ B/P4 остаются открытыми. Исходные ограничения канала и согласования остаются в [DECISIONS](DECISIONS.md); критерии A-03/A-05/A-07/A-08/A-09 — в [реестре](../spec/project.json).

## Что значит корректный перенос

На обоих ноутбуках доступны одинаковые операции экспорта, проверки и импорта в выбранную копию проекта. Приёмка включает цикл A → B → A с правками на каждом устройстве. Кодировка исходников не является транспортной кодировкой: файл читается и восстанавливается как последовательность байтов.

Разделяем три свойства: распаковка восстанавливает исходные байты; применение совместимо с принятой политикой рабочей копии; обычный Git diff показывает только реальные изменения относительно своей базы. Ни один из этих результатов сам по себе не доказывает остальные. Полный файл внутри пакета допустим: объём пакета не определяет размер Git diff.

Для нетронутых файлов запрещены повторная запись, смена EOL/BOM/encoding/EOF и file mode. Для изменённого файла сохраняется незатронутое содержимое; импорт не запускает formatter, organize imports, автоисправление пробелов или нормализацию всего проекта. Перемены mtime после записи реальной правки допустимы; mtime не заменяет проверку содержимого.

Первый импорт может создать новую копию; последующие импорты должны уметь применять принятые изменения к существующей рабочей копии. Пакет не переносит `.git`, историю, index, remotes, hooks и конфигурацию Git. Рабочие файлы изменяются только по принятому плану; staging/index сохраняется, включая уже staged правки.

## Общая база и локальная работа

Нужны подтверждённая базовая версия проекта и проверяемое состояние каждого затронутого пути. Сравниваются base/incoming/local; имя ветки и время файла не являются доказательством общей базы. База следующего обмена отражает реально подтверждённое применение. Отмена, конфликт или сам факт экспорта не обновляют её как успешный импорт.

В локальной реализации подтверждение всей входящей версии возможно только при точном совпадении итогового манифеста. Если сохранены дополнительные локальные изменения, нужен отдельный экспорт результата слияния и обратное подтверждение; весь incoming не объявляется общей базой автоматически. Начальный план без базы создаёт только отсутствующие файлы, пропускает одинаковые и блокирует замену различающихся существующих файлов.

Изменения в одном файле с обеих сторон считаются конфликтом, пока безопасный результат не определён явно. В MVP автоматический merge не обещается; пользователь разрешает конфликт отдельно и получает новый предпросмотр. Несвязанные локальные изменения остаются на месте. Отсутствие файла в выбранном экспорте не означает delete; удаление требует отдельного явного действия и подтверждения.

Перед записью нужно повторно проверить состояние, на котором был построен план. Если файл изменили после preview, старый план не применяется. Запись по нескольким файлам требует проверяемого восстановления после отмены/ошибки/прерывания; один атомарный rename не даёт многофайловой транзакции.

## Правила Git: проверенные факты и решение проекта

| Факт из официальной документации | Следствие для проектирования |
|---|---|
| `.gitattributes` задаёт `text`, `eol`, `working-tree-encoding`, `filter`, `ident`; дополнительные attributes могут приходить из `.git/info/attributes` и пользовательского файла. | Проверяем эффективные правила затронутых путей. Наличие одинакового файла `.gitattributes` ещё не доказывает одинаковую политику. [gitattributes](https://git-scm.com/docs/gitattributes), [check-attr](https://git-scm.com/docs/git-check-attr). |
| `core.autocrlf`, `core.eol`, `core.safecrlf`, `core.fileMode`, `core.symlinks` влияют на представление и поведение рабочей копии. Git учитывает executable bit, но не полный Windows ACL. | Проверяем обе копии без изменения global/local config; режимы и типы файлов рассматриваем отдельно от текста. [git config](https://git-scm.com/docs/git-config). |
| `git ls-files --eol` различает EOL в index и рабочем дереве. | Диагностика EOL дополняет проверку байтов. Команда здесь — будущий инструмент проверки, сейчас не запускалась на ноутбуках. [ls-files](https://git-scm.com/docs/git-ls-files). |
| `git hash-object --no-filters` хеширует исходные байты; режим с `--path` может применить фильтры по пути. | Обычный SHA не доказывает отсутствия Git diff. Незнакомые фильтры не запускаются автоматически ради сравнения. [hash-object](https://git-scm.com/docs/git-hash-object). |
| `git apply --3way` требует доступных базовых blobs и подразумевает `--index`. | Нельзя вызывать его в пользовательском repo, одновременно обещая неизменность staging. Планирование/разрешение конфликтов изолируется от реального index. [git apply](https://git-scm.com/docs/git-apply). |

Локальный MVP применяет только поддержанную политику `raw-v1`: `core.autocrlf` отсутствует либо `false`, `core.eol` отсутствует либо `lf`; эффективные `text`, `eol`, `working-tree-encoding`, `filter`, `ident` для выбранных путей должны быть `unspecified` либо `unset`. Выбранные записи index допускаются только как обычные файлы `100644`, stage 0; executable/symlink/gitlink, unmerged index, коллизии регистра и выбранный путь внутри submodule блокируют применение. Отсутствие Git или неизвестная политика также дают отказ; даже папка без репозитория требует доступного Git для проверки отсутствия правил.

Проверка использует ограниченные readonly builtin-команды `config`, `check-attr` и `ls-files --stage -z`, с отключёнными hooks/fsmonitor и без запуска filters, внешних diff/textconv или кода проекта. Автоматическое изменение Git config, `renormalize` и массовая нормализация не выполняются. Неподдерживаемая кодировка не является поводом перекодировать байты. Явная входящая смена BOM/EOL/encoding допускается как реальная правка источника при безопасном плане и переносится побайтно; приложение само ничего не преобразует. Адаптация к другой checkout-политике требует отдельного решения и приёмки.

При явной правке `.gitattributes` или иных правил это реальное изменение с возможным широким эффектом. Оно должно быть видно в плане; текущий MVP блокирует изменение `.gitattributes` как неподдерживаемое. Требование «одна строка» относится к сценарию, где политика не менялась. Бинарные файлы и некоторые кодировки не имеют обычного построчного diff — для них проверяются байты и отсутствие непредусмотренных изменений.

## Локальная запись и восстановление

`Capture` повторно использует ограниченный readonly scanner; манифест связывает относительные пути, исключения, хеши, представление и семантику Git-политики, без абсолютного корня. `Apply` принимает только неизменённый backend-план и заново проверяет текущую копию. Нетронутые файлы не открываются для записи. Изменение mode, readonly-файл и неподдерживаемый тип блокируются; Windows ACL не переносятся между ПК как POSIX mode.

Изменённые файлы публикуются через copy-on-write: новая версия полностью готовится и синхронизируется в отдельном файле, права существующего назначения копируются и проверяются, исходный объект переименовывается в резервное имя. Переименования по удерживаемым Windows handles не заменяют уже занятое имя. Ранее существовавшие потоки данных не перезаписываются, поэтому появившаяся конкурентно жёсткая ссылка сохраняет прежние байты. Каталоги закреплены handles; reparse points, короткие псевдонимы внутри области проекта и физическое пересечение проекта с журналом отклоняются.

Журнал и blob-резервы защищены Windows DPAPI текущего пользователя. Временные `.figmobil-old-*` и `.figmobil-new-*` в рабочем каталоге содержат открытые данные и исключены из снимка. Защита журнала не превращает рабочую папку в зашифрованную файловую систему; гарантированное физическое стирание не обещается. NTFS ADS не транспортируются: изменяемый существующий файл с именованными потоками, например `Zone.Identifier`, отклоняется до изменений рабочей копии; восстановление также проверяет потоки.

Между переименованиями существует промежуток; многофайловая операция не атомарна. Ошибка или отмена вызывает проверяемый rollback, а после прерывания процесса нужен явный `Recover`. Неизвестная новая версия либо занятое исходное имя не затираются: журнал остаётся для разбора. Наличие журнала блокирует новые операции до восстановления. Испытания прерывания процесса не дают гарантии восстановления после потери питания или повреждения файловой системы.

## Матрица приёмки и область доказательств

На синтетических Windows-копиях локально проверены обычный Git diff одной строки, нулевой diff повторного импорта, сохранение index/config и несвязанных staged/unstaged правок, нетронутых байтов/mtime, явные изменения BOM/EOL/UTF-16, пустые файлы, конфликт, устаревший план и восстановление. Отдельные native-проверки покрывают конкурентные hardlink/создание файла, protected/inherited ACL, reparse mutation, 8.3 aliases и отказ при ADS. Воспроизводимые сценарии: [файловые проверки](../internal/workspace/apply_windows_test.go), [представление](../internal/workspace/representation_test.go), [native Windows](../internal/workspace/native_windows_test.go), [конкурентное создание](../internal/workspace/replace_windows_test.go), [ADS](../internal/workspace/streams_windows_test.go). Общий локальный прогон D-16 дал 10/10 PASS, включая Go tests/vet и Windows build; артефакт — `.artifacts/local-verification.json`. Актуальные результаты и незакрытые проверки фиксируются в [STATE](STATE.md).

Таблица ниже сохраняет целевую приёмку, включая ещё не проверенные среды и ошибки. Для каждого случая на целевых ноутбуках проверяются оба направления; локальные fixtures и сквозной [синтетический тест шифрованного канала](../internal/channel/channel_test.go) не заменяют реальный Figma A → B → A, браузерную приёмку и проверки исходного проекта на обоих устройствах.

| Сценарий | Ожидаемое поведение |
|---|---|
| Одинаковая база, цикл A → B → A без правок | Ноль новых различий в Git и ноль записей в существующие неизменённые файлы |
| Одна изменённая строка | Только ожидаемая правка; остальные строки и файлы сохранены |
| Повторный импорт того же пакета | Явный результат already-applied/no-change; нет новых записей и различий |
| LF, CRLF, mixed EOL, EOF без newline | Исходные байты восстановлены; нет молчаливой нормализации при применении |
| UTF-8 с/без BOM, UTF-16, legacy encoding | Нет автоматического перекодирования; неизвестный текст переносится как байты |
| Пустой файл, бинарный файл, Unicode-путь | Корректные содержимое/путь или объяснённый отказ до записи |
| Разные attributes/autocrlf/encoding/filter rules | Отчёт о совместимости; неподдерживаемый случай блокируется, config не меняется |
| Разные branch/HEAD, нет подтверждённой базы | Явное несовпадение; имя ветки не позволяет слепой overwrite |
| Staged и unstaged локальные правки | Staging/index и несвязанные изменения сохранены, пересекающиеся показаны как конфликты |
| Изменение файла на обеих сторонах | Конфликт без last-write-wins и незаметного принятия одной версии |
| Delete/modify, rename/modify, case-only rename | Явный план; неоднозначный или несовместимый путь блокирует операцию |
| Отмена, ошибка, нехватка места, прерывание | Нет незаметного частичного успеха; восстановление проверено на файловой системе цели |
| Локальная правка после preview | Старые preconditions не прошли; запись не начинается или результат безопасно восстанавливается |
| Executable bit, неподдерживаемый тип/symlink | Нет неожиданной смены режима/типа; ограничение показано до записи |
| Проверки исходного проекта после A → B и B → A | Проходят выбранные lint/typecheck/test/build или native аналоги на каждом устройстве |

Git проверяется обычным diff/status относительно исходного состояния каждой копии. Нельзя скрывать шум через `-w`, `--ignore-space-at-eol`, `assume-unchanged` и подобные средства. Для машинной проверки выбираются внутренний diff без external diff/textconv и независящий от красивого UI отчёт. До/после отдельно сравниваются index и несвязанные изменения. [git diff](https://git-scm.com/docs/git-diff).

Все проверки imported project code запускаются отдельно в разрешённой тестовой среде после выбора команд; импорт сам не выполняет содержимое проекта. Проверка обвязки не заменяет ни одного сценария этой таблицы.
