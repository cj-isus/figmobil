# Архитектура локальной реализации

Прозрачный объём и канал Figma согласованы. Первый readonly-компонент D-11 — [локальное сравнение копий](LOCAL-COMPONENT.md). D-16 разрешил локальную реализацию ручного канала: Go-приложение, встроенные HTML/CSS/JS, защищённый loopback-интерфейс, age/Ed25519/Windows DPAPI и подтверждаемое применение. Реализация и синтетические тесты существуют; P1 целевых устройств, полная браузерная приёмка и реальный Figma A ↔ B/P4 остаются открытыми. Граница этапов — в [плане](PLAN.md).

## Выбор готового и стека

### Обязательная криптостойкость (D-14)

Пользователь потребовал: «шифр не должен легко разгадываться». В локальном P2T содержимое и имена файлов входят в подписанный пакет, зашифрованный получателю готовой библиотекой age; Base64 служит только текстовым представлением шифротекста. `internal/secure` использует age X25519 и стандартный Ed25519, а Windows DPAPI защищает локальные ключи и состояние. Функциональные проверки не являются независимым криптоаудитом.

- Долговременные ключи устройств генерируются криптографическим генератором; секретные части защищённо хранятся только локально и не попадают в Figma, пакет, Git, логи или память проекта. Новая случайность и сеансовый материал нужны каждому шифрованию; доверенные ключи получателя при каждом экспорте не меняются.
- Получатель выдаёт payload только после ограниченного чтения до аутентифицированного конца age-потока и проверки подписи ожидаемого отправителя, привязанной к получателю. Подмена, усечение, чужой ключ и неподтверждённый отправитель завершаются ошибкой до изменения рабочей копии или базы.
- Подписанный payload связывает project/package/base ID и manifest; подтверждения версий проходят тот же защищённый протокол. Шифрование адресату само по себе не подтверждает отправителя: это отдельно проверяет Ed25519.
- Подключение использует приглашение, ответ и ручную сверку кода на двух экранах; профиль требует подтверждения обеих сторон. Доступность такой сверки на целевых устройствах проверяется в P1/P4. Первый fingerprint, полученный только через неподтверждённый канал, не является независимой проверкой личности.
- Интеграционные проверки A-02 включают roundtrip, неверный ключ, изменение бита/метаданных, обрезку/перестановку частей, неподтверждённого отправителя, повтор и отсутствие секретов в выводе. Повторное шифрование одинакового пакета должно использовать свежую случайность. Тесты не доказывают математическую стойкость алгоритма; она опирается на выбранный исследованный дизайн и проверенную реализацию.

Спецификация [age](https://age-encryption.org/v1) описывает CSPRNG, свежий файловый ключ, ChaCha20-Poly1305 и обязательную проверку финального фрагмента. age реализует конфиденциальность; модель доверия figmobil дополнена подписью и подтверждением подключения. Абсолютная невзламываемость не обещается: защита зависит от реализации и сохранности конечных устройств/ключей; размер и время передачи могут быть видны.

Текущий UI — встроенные HTML/CSS/JavaScript с разделёнными моделью и контроллером; файловые операции выполняет Go backend. React/Vite, Tauri/Electron, отдельный Node-процесс и Figma-плагин не добавлялись. Браузерный интерфейс сам не получает произвольный доступ к файловой системе. Конкретные дополнительные установки на первом ноутбуке по-прежнему согласуются до выполнения.

Готовая Go library [age](https://github.com/FiloSottile/age) встроена в приложение; отдельная установка CLI age не требуется. Версия `filippo.io/age v1.3.2` и зависимости закреплены в [go.mod](../go.mod)/go.sum; происхождение и лицензии описаны в [DEPENDENCIES](../internal/secure/DEPENDENCIES.md). Сборка на текущем Windows-компьютере не заменяет проверку обеих целевых ОС.

Секретные ключи остаются в backend и защищённом локальном состоянии; в Figma передаются публичные данные подключения или зашифрованные пакеты. Свои криптопримитивы, «скрытый общий пароль» в Figma и хранение приватного ключа в документе не используются. Утрата ключей/защищённого профиля может сделать пакет невосстановимым; ротация не отзывает уже расшифрованные копии.

PostgreSQL, облачный backend, аккаунты сервиса, телеметрия и фоновые сетевые службы для локального MVP не нужны. Версии и контрольные суммы библиотек закреплены при сборке; это не разрешение дополнительных установок на целевые устройства.

## Границы компонентов

| Компонент | Ответственность | Граница |
|---|---|---|
| Project profile | Корень проекта, включения/исключения, разрешённый получатель | Не перечисляет каталоги за выбранным корнем |
| File selection | Список файлов и объяснение исключений | Не читает весь диск, не следует symlink по умолчанию |
| Package builder | Побайтовый снимок выбранных файлов, базовая версия и манифест | Без сети, изменения источника и упаковки `.git` |
| Crypto adapter | Вызов выбранного готового инструмента через узкий API | Ключи не попадают в UI-состояние/логи/CLI-строки |
| Package inspector | Валидация версии, структуры и целостности | Ничего не исполняет и не пишет до проверки |
| Base/version comparison | Сопоставление базовой, входящей и локальной версии в каждом направлении | Неизвестная база и расходящиеся правки не применяются вслепую |
| File fidelity / Git policy | Байты, представление файлов и диагностика атрибутов обеих рабочих копий | Без автоматической нормализации и исполнения внешних filters |
| Import planner | Неизменённые файлы, изменения и конфликты для выбранной рабочей копии | План доступен до применения; одинаковые файлы пропускаются |
| Import executor | Выборочная запись, повторная проверка preconditions и восстановление | Сохраняет index и нетронутые файлы, не переписывает проект целиком |
| Job state | Прогресс, отмена, результат и безопасный повтор | UI отображает подтверждённое состояние |
| Текстовое представление пакета для Figma | Ручное копирование шифротекста в/из содержимого текстового слоя | Без плагина в основном сценарии, приватных ключей/расшифрованного кода на холсте и фонового импорта; комплектность/порядок частей проверяются до применения |

Слои создаются по мере появления функций. Не создаём заранее пустые `apps/packages/features/entities/shared`. UI-компонент не выполняет файловые операции или криптографию напрямую; доменные функции не зависят от React/Figma. Новый общий компонент появляется после поиска пригодного аналога.

## Машинные контракты

Текущий источник истины — [spec/project.json](../spec/project.json): идентификаторы требований/функций/приёмки, этапы, ограничения, вопросы согласования. `scripts/project/check.mjs` проверяет согласованность реестра и файлов обвязки; это локальная подсказка процесса, не средство защиты от изменения самим пользователем и не доказательство его согласия.

Реализованы версионированные Go-типы и runtime validation для профиля, пакета, манифеста/базы, Git policy и плана. [Manifest/Snapshot](../internal/compare/capture.go) содержат контрольные суммы, представление, scope и policy; абсолютный корень не входит в переносимый манифест. Его ID детерминирован. [ApplyPlan](../internal/workspace/plan.go) задаёт preconditions и действия skip/create/replace/delete; конфликт блокирует план, delete требует явного намерения с ожидаемой базовой версией. План хранится и проверяется backend, действия из UI не принимаются. Входящий JSON недоверен до ограниченной проверки структуры; бинарные данные не помещаются в UI, текстовыми частями выдаётся шифротекст.

## Двусторонняя работа и сохранность файлов

Одинаковое ядро поддерживает экспорт/импорт на A и B уже в MVP. Общая подтверждённая база нужна для различения входящих и локальных изменений. Отсутствие базы, другой проект, расходящаяся версия и повторный пакет — явные состояния; совпадение путей не доказывает совместимость. Параллельные изменения одного файла без безопасно определённого результата дают конфликт; автоматический merge откладывается.

Хеши исходных байтов отделены от сравнения представления по Git-политике назначения. Текущий writer поддерживает только `raw-v1`: без checkout-преобразований, активных text/eol/encoding/filter/ident attributes и с обычными index mode `100644`, stage 0. Политика проверяется ограниченными readonly `config`, `check-attr`, `ls-files --stage -z`; hooks/fsmonitor отключены, filters и код проекта не запускаются. Неизвестная политика, executable/symlink/submodule/unmerged case и изменение `.gitattributes` блокируют применение. Точные ограничения — [FILE-FIDELITY](FILE-FIDELITY.md). Явная правка исходных BOM/EOL/encoding передаётся побайтно; автоматического renormalize, форматирования или изменения Git config нет. Полные файлы в пакете не определяют размер Git diff.

Нетронутые файлы не записываются повторно. При COW-замене Windows ACL существующего назначения копируется и проверяется, а mode не меняется; readonly и неподдерживаемые режимы блокируются. Режимы POSIX и Windows ACL не взаимозаменяемы. Синтетические файловые тесты подтвердили обычный Git diff одной строки, сохранение index/config и чужих staged/unstaged правок; это отдельное доказательство от ещё открытого A ↔ B на двух целевых ПК. Контракт и полная матрица — [FILE-FIDELITY](FILE-FIDELITY.md).

UI и backend различают ожидание, проверку/предпросмотр, выполнение, результат и ошибку; профиль отдельно хранит этап подключения, комплектность частей, ожидание подтверждения и `needsRecovery`. Для импорта «проверен» и «применён» — разные результаты. Сбой или отмена не объявляются успехом. Модели/контроллеры покрыты автоматическими тестами; полный браузерный сценарий текущего мастера ещё требует приёмки.

Экспорт/импорт запускаются только явными командами отдельных кнопок. Из `idle` нельзя стартовать по таймеру, изменению файла, появлению входящих данных или восстановлению предыдущей сессии. File watchers, фоновый polling, расписания и постоянная синхронизация не входят в архитектуру. Выполняется только выбранное задание; после результата система ждёт следующего нажатия. Возобновление прерванной операции требует нового явного действия.

## Границы безопасности и устойчивости

Доверяем выбранному локальному инструменту и конкретному получателю; внешние пакеты и имена файлов считаем недоверенными. Шифрование не защищает от скомпрометированного конечного ноутбука, съёмки экрана и чтения уже расшифрованных файлов. Названия проектов и метаданные тоже могут быть чувствительными: в необязательную доску статусов они не уходят без явного выбора.

Входящие пути проверяются на абсолютные/UNC/device forms, `..`, Windows device names и ADS-синтаксис; symlink/junction, короткие псевдонимы внутри project scope и коллизии регистра/структуры не допускаются к записи. Контракт требует безопасной обработки неоднозначных Unicode-путей и проверки целевых систем. Именованные NTFS-потоки не транспортируются; наличие ADS у изменяемого существующего файла или объекта восстановления даёт fail-closed отказ до изменений рабочей копии. Количество файлов, байты, metadata, глубина, размеры пакета/частей и чтение внешнего JSON ограничены ядром. Исполнение проекта или произвольная распаковка архива не используются.

Payload сначала полностью аутентифицируется и проверяется в ограниченной памяти backend. После предпросмотра и явного подтверждения writer заново проверяет снимок и удерживает Windows handles файлов/каталогов. Новые данные готовятся отдельно, исходный объект переименовывается в aside, затем новая версия занимает свободное имя через no-replace rename. COW не пишет в старый stream и сохраняет его конкурентные hardlink aliases. Существующий файл с неподдерживаемыми свойствами блокируется; чужое занятое имя не заменяется.

DPAPI защищает журнал и blob-резервы в локальной папке приложения. В рабочем каталоге временные `.figmobil-old-*`/`.figmobil-new-*` содержат открытые данные и исключены из снимка. Между rename есть промежуток: операция не является атомарной транзакцией. Ошибка/отмена запускает rollback; прерванный процесс требует явного `Recover`, а неизвестная поздняя версия сохраняется и блокирует автоматическое восстановление. Marker журнала блокирует следующие операции до разбора. Проверки process-crash recovery не обещают устойчивость к потере питания; файловая система и целевые устройства принимаются отдельно.

Логи: код ошибки, job ID и безопасные счётчики; без plaintext, ключей, токенов и содержимого файлов. Очистка временных файлов — хозяйственная операция, без обещаний гарантированного физического стирания на SSD или серверах Figma. Отчёт об успешном локальном импорте не доказывает сетевую доставку.

## Figma

Пользователь подтвердил разрешение передачи кода через Figma (D-10), путь без плагина (D-13) и локальную реализацию (D-16): [ручная вставка зашифрованного текста на холст и копирование содержимого слоя](TRANSPORT.md). На каждом ПК один локальный root; incoming и подтверждённая база управляются приложением. Локальный backend реализует подключение, подпись/шифрование, ограниченные текстовые части, приём, план/применение и обратные подтверждения. Общий rate gate допускает готовую часть ≤250 000 байт не чаще раза в 3 секунды, без burst; один владелец процесса на устройство и стартовый cooldown защищают выдачу приложения. Это не ограничение сетевого трафика самой Figma.

Все межПК пакеты и подтверждения пользователь переносит через Figma; автоматического чтения/стирания холста нет. Работа обычно поочерёдная, merge с коллегами ручной. Постоянная синхронизация исключена; удаление всех серверных копий не гарантируется. Проверенные ограничения — в [исследовании](FIGMA.md). Побайтовая сохранность canvas copy/paste, допустимые размеры, синхронизация и полный сценарий двух ноутбуков ещё не проверены; локальные синтетические тесты не закрывают P1/P4 или браузерную приёмку.
