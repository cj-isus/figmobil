# Предлагаемая архитектура

Прозрачный объём и канал Figma согласованы. По D-11 первый компонент — [локальное сравнение копий](LOCAL-COMPONENT.md) без плагина: Go standard library, встроенные HTML/CSS/JS, защищённый loopback-интерфейс. Остальные разделы описывают будущий перенос, который ещё не реализован. P1 целевых устройств остаётся открытым; [план](PLAN.md) отделяет независимый P2 от последующего P2T.

## Выбор готового и стека

### Обязательная криптостойкость (D-14)

Пользователь потребовал: «шифр не должен легко разгадываться». Для будущего P2T это обязательное сквозное шифрование содержимого и имён файлов готовой поддерживаемой библиотекой. Base64/текстовое представление служит только переносу уже зашифрованных байтов через Figma. Криптокод текущего preview отсутствует; стойкость реализации ещё не проверена.

- Долговременные ключи устройств генерируются криптографическим генератором; секретные части защищённо хранятся только локально и не попадают в Figma, пакет, Git, логи или память проекта. Новая случайность и сеансовый материал нужны каждому шифрованию; доверенные ключи получателя при каждом экспорте не меняются.
- Нужна полная проверка аутентифицированного шифрования, включая завершение потока, и проверка доверенного отправителя до изменения рабочей копии или общей базы. Расшифрованный префикс может существовать только как недоверенные staging-данные. Подмена, усечение, чужой ключ и неподтверждённый отправитель завершаются ошибкой.
- Аутентификация должна связывать содержимое с project/package/base ID и manifest, а также защищать подтверждения версий. Шифрование адресату само по себе не подтверждает отправителя. Модель sender authentication выбирается отдельно с готовыми примитивами/инструментами.
- Способ первичного доверия к ключам должен быть определён до первого реального переноса. Первый fingerprint, полученный только через тот же неподтверждённый канал, не является независимой проверкой личности.
- Интеграционные проверки A-02 включают roundtrip, неверный ключ, изменение бита/метаданных, обрезку/перестановку частей, неподтверждённого отправителя, повтор и отсутствие секретов в выводе. Повторное шифрование одинакового пакета должно использовать свежую случайность. Тесты не доказывают математическую стойкость алгоритма; она опирается на выбранный исследованный дизайн и проверенную реализацию.

Спецификация [age](https://age-encryption.org/v1) описывает CSPRNG, свежий файловый ключ, ChaCha20-Poly1305 и обязательную проверку финального фрагмента. age остаётся кандидатом для конфиденциальности, а не готовой моделью доверия figmobil. Абсолютная невзламываемость не обещается: защита зависит от реализации и сохранности конечных устройств/ключей; размер и время передачи могут быть видны.

Кандидат для UI — TypeScript strict, React и Vite: компонентный интерфейс и небольшое локальное приложение. Оболочку и доступ к файлам выбираем только после выяснения разрешённых установок и ОС. Tauri/Electron, локальный Node-процесс или Figma-плагин не считаются уже выбранными или разрешёнными. Браузерный интерфейс не даёт произвольного доступа к файловой системе автоматически.

Кандидат для шифрования файлов — готовый [age](https://github.com/FiloSottile/age), а не собственный формат шифрования. Официальный проект предоставляет CLI и Go library, лицензию BSD-3-Clause и установку для Windows. Это кандидат, а не установленная зависимость: перед выбором проверяются актуальный release, происхождение бинарника, лицензия, совместимость и тесты на целевых ОС. Встраивание Go-библиотеки в TypeScript не предполагается.

Шифрование получателю само по себе не доказывает личность отправителя. До принятия A-02 отдельно выбираем модель аутентичности: какой отправитель доверен и как сверяется его ключ/подпись. Свои криптопримитивы, «скрытый общий пароль» в Figma и хранение приватного ключа в документе не проектируются. Утрата приватного ключа может сделать пакет невосстановимым; ротация не отзывает уже расшифрованные копии.

PostgreSQL, облачный backend, аккаунты сервиса, телеметрия и фоновые сетевые службы для локального MVP не нужны. Версии и lockfile приложения фиксируются после выбора стека и разрешения установки зависимостей.

## Границы компонентов

| Компонент | Ответственность | Граница |
|---|---|---|
| Project profile | Корень проекта, включения/исключения, разрешённый получатель | Не перечисляет каталоги за выбранным корнем |
| File selection | Список файлов и объяснение исключений | Не читает весь диск, не следует symlink по умолчанию |
| Package builder | Побайтовый снимок выбранных файлов, базовая версия и манифест | Без сети, изменения источника и упаковки `.git` |
| Crypto adapter | Вызов выбранного готового инструмента через узкий API | Ключи не попадают в UI-состояние/логи/CLI-строки |
| Package inspector | Валидация версии, структуры и целостности | Ничего не исполняет и не пишет до проверки |
| Base/version comparison | Сопоставление базовой, входящей и локальной версии в каждом направлении | Неизвестная база и расходящиеся правки не применяются вслепую |
| File fidelity / Git policy | Байты, представление файлов и диагностика атрибутов обеих рабочих копий | Без автоматической нормализации и исполнения внешних filters |
| Import planner | Неизменённые файлы, изменения и конфликты для выбранной рабочей копии | План доступен до применения; одинаковые файлы пропускаются |
| Import executor | Выборочная запись, повторная проверка preconditions и восстановление | Сохраняет index и нетронутые файлы, не переписывает проект целиком |
| Job state | Прогресс, отмена, результат и безопасный повтор | UI отображает подтверждённое состояние |
| Текстовое представление пакета для Figma | Ручное копирование шифротекста в/из содержимого текстового слоя | Без плагина в основном сценарии, приватных ключей/расшифрованного кода на холсте и фонового импорта; комплектность/порядок частей проверяются до применения |

Слои создаются по мере появления функций. Не создаём заранее пустые `apps/packages/features/entities/shared`. UI-компонент не выполняет файловые операции или криптографию напрямую; доменные функции не зависят от React/Figma. Новый общий компонент появляется после поиска пригодного аналога.

## Машинные контракты

Текущий источник истины — [spec/project.json](../spec/project.json): идентификаторы требований/функций/приёмки, этапы, ограничения, вопросы согласования. `scripts/project/check.mjs` проверяет согласованность реестра и файлов обвязки; это локальная подсказка процесса, не средство защиты от изменения самим пользователем и не доказательство его согласия.

В реализации потребуются версионированные схемы `ProjectProfile`, `PackageManifest`, `BaseSnapshot`, `GitPolicyReport`, `ImportPlan`, `JobProgress` и `OperationResult`. Манифест связывает пакет с проектом/базовой версией и хранит контрольные суммы; ImportPlan задаёт для каждого пути ожидаемое локальное состояние и действие skip/create/update/conflict/delete (delete только по явному выбору). TypeScript-типы следует выводить из выбранной схемы валидации, чтобы не поддерживать независимо две копии. JSON извне — `unknown` до проверки. Бинарные данные не гоняются через компоненты как Base64-строки.

## Двусторонняя работа и сохранность файлов

Одинаковое ядро поддерживает экспорт/импорт на A и B уже в MVP. Общая подтверждённая база нужна для различения входящих и локальных изменений. Отсутствие базы, другой проект, расходящаяся версия и повторный пакет — явные состояния; совпадение путей не доказывает совместимость. Параллельные изменения одного файла без безопасно определённого результата дают конфликт; автоматический merge откладывается.

Хеши исходных байтов отделяются от сравнения представления по Git-политике назначения. Перед записью проверяются attributes/config обеих копий, encoding, EOL, BOM, EOF и mode. В MVP при неподдерживаемой или несовместимой политике операция останавливается с объяснением; никакого автоматического renormalize, форматирования или изменения Git config. Пакет может содержать полные файлы: размер пакета и точность Git diff — независимые свойства.

Нетронутые файлы не записываются повторно. Изменённый файл должен сохранить байты незатронутого содержимого и принятый mode. Режимы POSIX и Windows ACL не взаимозаменяемы; доступность executable bit и регистрозависимых имён проверяется на целевых системах. Контракт и будущие проверки — [FILE-FIDELITY](FILE-FIDELITY.md).

Планируемые состояния: `idle`, `validating`, `preview`, `running`, `succeeded`, `cancelled`, `failed`. Для импорта результат обязан различать «проверен», «подготовлен» и «применён». Сбой или отмена не переводятся в `succeeded`. Точную схему переходов и коды ошибок утверждаем в P2 до UI.

Экспорт/импорт запускаются только явными командами отдельных кнопок. Из `idle` нельзя стартовать по таймеру, изменению файла, появлению входящих данных или восстановлению предыдущей сессии. File watchers, фоновый polling, расписания и постоянная синхронизация не входят в архитектуру. Выполняется только выбранное задание; после результата система ждёт следующего нажатия. Возобновление прерванной операции требует нового явного действия.

## Границы безопасности и устойчивости

Доверяем выбранному локальному инструменту и конкретному получателю; внешние пакеты и имена файлов считаем недоверенными. Шифрование не защищает от скомпрометированного конечного ноутбука, съёмки экрана и чтения уже расшифрованных файлов. Названия проектов и метаданные тоже могут быть чувствительными: в необязательную доску статусов они не уходят без явного выбора.

Импорт должен отклонять абсолютные/UNC-пути, `..`, Windows device names, NTFS alternate data streams, symlink/junction и коллизии регистра/Unicode. Нужны пределы количества файлов, распакованного объёма, глубины путей и времени обработки; значения выбираются на синтетических fixtures в P1/P2. Если используется архивная библиотека, её поведение проверяется до выбора; самописный распаковщик не нужен.

Данные сначала проверяются в ограниченном временном каталоге. После предпросмотра результат либо создаёт новую копию, либо выборочно применяется к указанной рабочей копии. Перед записью повторно проверяется ожидаемое состояние файлов; изменившиеся во время предпросмотра файлы не затираются. Требуются восстанавливаемый план и ограниченная область записи, чтобы ошибка/отмена не оставляла частичного результата. Атомарность и crash recovery на конкретной ОС/файловой системе проверяются отдельно; гарантии многофайловой атомарности не выводятся из одного rename.

Логи: код ошибки, job ID и безопасные счётчики; без plaintext, ключей, токенов и содержимого файлов. Очистка временных файлов — хозяйственная операция, без обещаний гарантированного физического стирания на SSD или серверах Figma. Отчёт об успешном локальном импорте не доказывает сетевую доставку.

## Figma

Пользователь подтвердил разрешение передачи кода через Figma (D-10) и уточнил основной путь без плагина (D-13): [ручная вставка зашифрованного текста на холст и копирование содержимого слоя](TRANSPORT.md). На каждом ПК один локальный root; incoming из пакета и подтверждённая база управляются приложением. Расшифровка/сравнение выполняются локально, все межПК пакеты и подтверждения проходят Figma. Обычно работа поочерёдная, merge с коллегами ручной. Постоянная синхронизация исключена; удаление всех серверных копий не гарантируется. Проверенные ограничения — в [исследовании](FIGMA.md). Побайтовая сохранность canvas copy/paste, размеры/части и синхронизация требуют прототипа на синтетических данных; работающий канал пока не создан.
