# Frontend и PostgreSQL

## Найти существующее

1. Прочитать MAP и применимые правила; искать через rg по назначению,
   названию, props/типам, API endpoint и таблицам в затронутой области.
2. Перед новым компонентом/хуком/утилитой проверить реализации, варианты,
   stories/примеры, публичные экспорты и потребителей найденного API.
   Выбрать reuse или совместимое расширение; новое обосновать отсутствующим
   поведением, а не неудобным названием существующего.
3. Исследовать фактическую структуру и границы компонентов проекта. hooks/data/lib
   внутри компонента, share или shared/lib — примеры, не обязательные папки.
   Максимально выделять осмысленные компоненты с ясной ответственностью и reuse;
   не дробить искусственно, не переименовывать каталоги и не навязывать FSD.

## Изменить компонент и поток данных

- Сохранять публичные экспорты, props/типы и существующих потребителей;
  менять контракт только в объёме задачи с обновлением затронутых вызовов.
- Использовать принятые hooks, API-клиент, cache/query keys, схемы валидации,
  формы и утилиты. Проверить варианты/настройки библиотеки до нового аналога.
- Проследить затронутый путь: UI → hook/state/cache → API → запрос → ответ.
  Логику данных размещать по существующей границе, не дублировать в компонентах.
- Для изменяемого асинхронного поведения проверить loading/error/empty,
  повторный запрос, устаревший ответ, инвалидацию и повторную отправку там,
  где они влияют на сценарий. Сохранять семантику и доступность управления.

## PostgreSQL — только когда затронут

- Сначала найти фактическую schema, историю миграций, ORM/query builder,
  транзакционные границы, ограничения и тестовую конфигурацию проекта.
  Не придумывать названия таблиц и не добавлять второй способ доступа к БД.
- Значения передавать параметризованными запросами. Динамические имена
  колонок/сортировки брать из разрешённого набора и экранировать средствами
  принятой библиотеки; пользовательский ввод не вставлять в SQL строкой.
- Выпущенные миграции не переписывать: добавить следующую в принятом формате.
  Для изменения данных/ограничений учесть совместимость кода, существующие
  строки, блокировки и размер таблицы; индексы обосновывать запросом/планом.
- Проверить миграцию на отдельной тестовой БД: создание с нуля и обновление
  предыдущей схемы с характерными данными; rollback — если он предусмотрен.
  Проверить изменённые запросы и ограничения интеграционным сценарием.
  Отсутствие доступа к БД не считается пройденной проверкой; указать пробел.
  Production-миграцию выполнять только в рамках явно разрешённого запуска.

## Завершить

Запустить проверки затронутого поведения и команды проекта. В результате
указать переиспользованное, изменение публичных/DB-контрактов и фактически
выполненные проверки; отдельно назвать непроверенное. Не создавать копии
этих правил в документации проекта.
