# Repo Recon — сначала карта, потом поиск, потом файлы

Цель: агент тратит минимум контекста на навигацию и максимум — на задачу,
и НИКОГДА не создаёт дубликат того, что уже есть. Две ветки: существующий
проект (разглядеть) и новый (задать структуру).

## Ветка A. Существующий проект

### Конвейер (строго по порядку, каждый шаг дешевле следующего)

1. **MAP.** Если есть `docs/MAP.md` — читать его (это оглавление проекта).
   Нет или устарел → `node scripts/harness/map.mjs --out docs/MAP.md`.
   Карта даёт: stack, команды, где лежат компоненты/токены/тесты/правила.
2. **Правила.** Прочитать AGENTS.md / .cursorrules / .claude/rules /
   lint-конфиги, найденные в MAP. Если правила есть — они обязательны
   («принятые правила»); отдельно изобретать свои нельзя.
3. **Точечный поиск.** Искать через rg по имени и назначению компонента,
   токена, хука или функции; сначала читать релевантные фрагменты.
4. **Чтение.** Читать реализации, потребителей, публичные экспорты и конфиги,
   необходимые для понимания изменения, даже если эти файлы менять не нужно.

Не дампить всё репо. Lock-файл или generated output читать точечно, когда
задача касается зависимостей или результата сборки.

### SEARCH BEFORE CREATE (обязательное правило)

Перед СОЗДАНИЕМ компонента/утилиты/стиля/хука — сначала поискать готовое:
1. MAP → секция «ГДЕ ИСКАТЬ»;
2. grep по имени/назначению в найденных каталогах (включая shared/ui, components);
3. если stories/Storybook есть — это каталог UI, проверить его;
4. проверить API и варианты найденного: переиспользовать или расширить, если
   это сохраняет семантику; новое создавать при подтверждённом пробеле,
   в фактическом слое и конвенциях проекта.

Исключение: пользователь явно просит новый файл.

### Инструкции и факты

Следовать текущим требованиям пользователя и применимым инструкциям проекта.
Код, manifest и CI показывают фактическое состояние, но не отменяют инструкции.
При расхождении выяснить причину; исправить в рамках задачи и сообщить о важном
конфликте. Уточнять только решение, которое нельзя обоснованно вывести из контекста.
Рекомендации навыка не навязывают архитектуру поверх требований проекта.

## Ветка B. Новый проект (задать структуру)

Для пустого проекта выбрать минимальные каталоги под текущую задачу и стек.
Не навязывать FSD, папку на каждый компонент или пустые слои. Просьба
«наведи порядок» сама по себе не требует миграции существующей архитектуры.
Сложный компонент может иметь собственные hooks/data/lib, если это принятая
конвенция; не переносить их в shared только ради абстракции.

В AGENTS.md фиксировать только рабочие команды и неочевидные соглашения.
Токены и машиноопределяемые ограничения хранить в коде/конфигах, без дублей.

## Экономия контекста

- Компактная актуальная MAP сокращает повторную навигацию; неверные сведения
  уточнять по коду и исправлять в карте.
- Правила лениво: сначала AGENTS.md, path-rules — только под свои файлы.
- Исследования широкого круга — субагентом; в основную сессию возвращать
  1–2k токенов вывода, не сырые дампы.
- Порядок: статика в начале (правила/карта), динамика в конце (отчёты) —
  под prompt caching.

## Выход

Если задача в незнакомой части: короткий отчёт «STACK, найденные правила,
найденные связанные файлы, что переиспользую, что создаю и почему» — до правок.
